1. HOW TENANT ISOLATION WORKS
================================================================================

PRIMARY MECHANISM: PostgreSQL Schema Isolation
- Each tenant has separate schema: tenant_{tenantID}
- Connections use search_path to restrict to tenant schema
- Database enforces isolation at connection level
- Example: tenant_yumna_bertigamart, tenant_tika_nusseyba

CONTEXT PROPAGATION: JWT Token
1. User login → System searches ALL tenants
2. User found in specific tenant's schema
3. JWT generated with tenantID claim
4. Every request validated against JWT

7. THREAT ANALYSIS
================================================================================

Threat: Cross-Tenant Data Access
  Path: API request → Handler → Repository → Database
  Protection 1: JWT validation (extracts tenantID)
  Protection 2: Schema routing (search_path set in DSN)
  Protection 3: App filtering (WHERE tenant_id = ?)
  Risk Level: 🟢 LOW (multiple layers)

Threat: JWT Token Theft
  Path: Attacker steals another user's JWT
  Protection 1: Token signed with secret
  Protection 2: Short expiration (typically 1 hour)
  Protection 3: tenantID locked in token
  Risk Level: 🟢 LOW (tenant-bound)

Threat: SQL Injection
  Path: Attacker injects SQL in input parameters
  Protection 1: GORM parameterized queries
  Protection 2: No string concatenation
  Protection 3: Schema isolation as fallback
  Risk Level: 🟢 LOW (multiple layers)

Threat: Database Credential Compromise
  Path: Attacker gains PostgreSQL login credentials
  Protection 1: Stored in environment variables
  Protection 2: Search_path in connection string
  Protection 3: Recommended: VPC security groups
  Risk Level: 🟠 MEDIUM (requires separate hardening)
